# 커밋

git 커밋 할 때 사용한다.
커밋 메시지는 Conventional Commits 형식을 지킨다.
`main`에 직접 푸시를 금지한다.

---

## 형식

```
<type>: <subject>
```

- **기본 스타일**: Conventional Commits (`feat:`, `fix:`, `docs:`, `test:`, `chore:` 등)
- **스코프 괄호는 기본적으로 안 쓴다** — `type(scope):` 형태는 사용자가 명시적으로 요청할 때만 붙인다. 모노레포에서 패키지 구분이 필요하다는 합의가 저장소에 있으면 그때만 `feat(core):` 처럼 쓴다.
- **제목**: 한국어 명사형 종결, 마침표 없음, 72자 이내
- **본문**(선택): 제목 다음 한 줄 비우고, 72자에서 줄바꿈, *무엇*이 아니라 *왜*를 쓴다

---

## 타입

| 타입       | 언제 쓰나                                         | 예시                                        |
| ---------- | ------------------------------------------------- | ------------------------------------------- |
| `feat`     | 사용자에게 보이는 새 기능·동작                    | `feat: 도착 목록 가상 스크롤 적용`          |
| `fix`      | 버그 수정                                         | `fix: 탭 복귀 시 소켓 중복 구독 차단`       |
| `docs`     | 문서, README, 가이드, 스킬 파일, 주석만 고친 변경 | `docs: FSD 레이어 import 규칙 설명 추가`    |
| `refactor` | 동작 변화 없는 구조 변경                          | `refactor: 도착 폴링을 useArrival로 분리`   |
| `test`     | 테스트, 픽스처, 검증 스크립트                     | `test: ErrorBoundary 폴백 렌더 테스트 추가` |
| `perf`     | 동작은 그대로, 성능만 개선                        | `perf: 노선 폴리라인 계산 메모이제이션`     |
| `build`    | 빌드 설정, 의존성, 번들러, 패키징                 | `build: vite 8.0.10으로 올림`               |
| `ci`       | CI/CD 설정과 자동화                               | `ci: 빌드 잡에 pnpm 캐시 추가`              |
| `chore`    | 그 밖의 저장소 관리(에디터 설정, 런타임 버전)     | `chore: .nvmrc 추가`                        |

정리해 둘 것:

- 코드 변경이면 `feat` 과 `fix` 를 우선 고른다.
- `.claude/` 아래 스킬·규칙 문서는 `docs` 다.
- 의존성 추가·삭제·버전 변경은 `chore` 가 아니라 `build` 다. 빌드·번들러 설정도 같다.
- `Revert`, `Merge` 는 git 이 만들어 주는 타입이다. 직접 쓰지 않는다.

## 규칙

### 1. 제목줄

- **명사형 종결**: `추가`·`정리`·`수정`으로 끝낸다. `~한다`·`~했다`는 쓰지 않는다.
- **마침표 없음**
- **72자 이내** — git log 서식이 깨지는 지점이라 이건 상한이다.
- **어떻게가 아니라 무엇이 바뀌었는지**: `fix: 도착 조회 폴링 주기 정정` 이 맞고, `fix: 3000을 15000으로 변경` 은 틀리다.

### 2. 본문

이럴 때 본문을 붙인다.

- 변경이 한눈에 안 들어올 때 (미묘한 버그 수정, 설계 판단)
- 다른 사람이 알아야 할 제약이나 주의점이 있을 때
- PR 안에 커밋이 여러 개고 각각 맥락이 필요할 때

```
feat: SharedWorker로 탭 간 웹소켓 연결 공유

탭마다 소켓을 따로 열어서 서버 커넥션이 탭 수만큼 늘어났다.
SharedWorker 하나가 소켓을 소유하고, 탭은 postMessage 로 구독만 한다.

- shared-socket.worker.ts: 소켓 소유, 구독자 관리, 재연결 백오프
- useSharedSocket.ts: 워커 연결/해제 훅
- vite.config.ts: worker 번들 포맷을 es 로 고정
```

본문에서 더 지키는 것:

- diff를 요약하지 않는다. diff를 읽어서는 알 수 없는 판단 근거만 쓴다.
- 검증 결과는 값으로 적는다(`118 tests`). 통과 여부만 적지 않는다.
- 되돌리기 어려운 변경(질의 키·공개 API·계약)은 무엇이 바뀌었는지 한 줄 남긴다.
- `Co-Authored-By` 서명은 항상 붙인다.

### 3. PR에 들어가는 커밋

- 커밋 메시지만 읽고도 이해되게 쓴다. PR 설명에 기대지 않는다.
- 이슈를 닫으면 본문에 `Closes #2` 로 남긴다. 제목에는 쓰지 않는다.
- 제목 끝의 `(#N)` 은 squash merge 할 때 GitHub이 붙인다. 로컬 커밋에 직접 쓰지 않는다.

### 4. 스쿼시 · 리워드

PR 전에 히스토리를 정리할 때 지킨다.

- 메시지만 고치는 리워드는 원래 `Author` 를 유지한다. 사용자가 직접 요청하지 않는 한 `--reset-author` 를 쓰지 않는다.
- 이미 푸시한 브랜치를 스쿼시하거나 리워드하면 히스토리가 다시 쓰인다. `--force-with-lease` 로 푸시한다. 그냥 `--force` 는 쓰지 않는다.

### 5. 파일을 여러 개 건드린 커밋

파일 목록이 아니라 **의도**를 제목에 쓴다.

```
# 좋음
feat: 실패한 인쇄 작업 오프라인 큐 추가

# 나쁨
printer.ts, queue.ts, config.ts, index.ts, types.ts 수정
```

### 6. 쓰지 말 것

- 두루뭉술한 메시지: "코드 수정", "버그 수정", "이것저것"
- main 에 올라가는 WIP 커밋: "wip", "temp", "test" — 브랜치를 쓴다
- 제목에 파일 목록: "foo.ts와 bar.ts 수정"
- 서술형 종결: "추가했다", "고쳤음" — 명사형으로
- 이모지 — 저장소가 이미 쓰고 있을 때만

## 판단 순서

```
새로 생긴 기능인가?
  YES → feat: <무엇이 가능해졌는지>
  NO ↓

버그 수정인가?
  YES → fix: <무엇이 고장나 있었는지>
  NO ↓

동작은 그대로고 구조만 바꿨나?
  YES → refactor: <무엇을 재배치했는지>
  NO ↓

파일·스크립트·예제를 새로 추가했나?
  YES → 문서·스킬이면 docs, 테스트 픽스처면 test,
        저장소 관리용이면 chore, 사용자에게 보이면 feat
  NO ↓

설정·의존성·버전 변경인가?
  YES → 의존성/빌드/Docker 면 build, CI 면 ci, 그 외 관리성이면 chore
  NO ↓

사소한 변경인가? (오타, 주석)
  YES → 문서 오타면 docs, 그 밖에는 chore
  NO → 가장 가까운 타입을 고른다
```

## 빠른 템플릿

대부분의 변경은 이 틀만 채우면 된다.

```
<type>: [<어디에>] <무엇을> <명사형 동작>
```

- `feat: 실패한 인쇄 작업 오프라인 큐 추가`
- `fix: 도착 조회 폴링 주기 정정`
- `docs: FSD 레이어 import 경계 문서화`
- `test: 소켓 재연결 일관성 픽스처 추가`
- `refactor: ZPL 빌더를 별도 패키지로 분리`
- `build: vite 8.0.10으로 올림`
- `chore: 내부 전용 스킬 참조 제거`

## 커밋 크기와 분할

- 하나의 커밋은 하나의 목적을 가진다. type 하나로 설명되지 않으면 나눈다.
- 상한 **200줄**(추가+삭제), **파일 8개**. 잠금파일(`pnpm-lock.yaml`)과 생성물은
  집계에서 뺀다.
- 기능 변경과 이름·서식 변경은 한 커밋에 넣지 않는다.
- 중간 상태가 깨지는 분할은 하지 않는다. 타입 시그니처가 바뀌어 소비처가 함께
  고쳐져야 하면 한 커밋으로 둔다.
- 나눌 수 없어 상한을 넘길 때는 그 이유를 본문에 적는다(예: 슬라이스 전체 이름 변경).
- 한 파일 안에 목적이 다른 변경이 섞였으면 파일 단위로 나눌 수 없다. `git diff`로
  패치를 뽑아 필요한 부분만 남기고 `git apply --cached`로 스테이징한다
  (`git add -p`는 대화형이라 이 환경에서 쓸 수 없다).

## 순서

1. `git status --short`와 `git diff`로 변경 사항을 읽는다.
2. 위 기준으로 최소한의 논리적 단위로 나눈다. 같은 파일 안에서 관심사가 섞였으면
   변경 덩어리 단위로 나눈다.
3. 커밋 메시지 초안을 보여 주고 **멈춘다.**
4. 사용자가 지시하면 그때 `git add`와 `git commit`을 실행한다.

## 스테이징

- `git add -A`를 쓰지 않는다. 커밋할 경로를 직접 지정한다.
- 추적되지 않는 파일은 커밋 대상인지 먼저 확인한다.

## 커밋 후

- 무엇을 커밋했고 워킹트리에 무엇이 남았는지 보고한다.
- 푸시·PR 생성은 별도 승인을 받는다.
